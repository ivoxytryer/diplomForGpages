# API-контракт для FastAPI

Документ описывает HTTP-контракт, который ожидает фронтенд `hr-system`.
Сейчас его реализует мок-сервер MSW (`src/mocks/handlers.ts`), но URL, параметры,
тела запросов и ответы совпадают с тем, что должен отдавать реальный бэкенд.

- **Базовый префикс:** `/api/v1` (настраивается через `VITE_API_URL`)
- **Формат:** JSON, `Content-Type: application/json`
- **Даты:** `YYYY-MM-DD`; месяцы — `YYYY-MM`; дата-время — ISO 8601
- **Деньги:** целые числа в рублях
- **Идентификаторы:** строки
- **Ошибки:** `{ "detail": "Текст ошибки" }` + корректный HTTP-статус
- **Валидация формы (опционально):** `{ "detail": "...", "fields": { "email": "Некорректный email" } }`

Авторизация — заголовок `Authorization: Bearer <token>` для всех эндпоинтов, кроме `POST /auth/login`.
При `401` фронтенд автоматически разлогинивает пользователя (кроме запроса логина).

**Чтение также требует авторизации.** Сервер применяет scope: `employee` видит только
себя, `manager` — своё подразделение с дочерними и команды своих проектов, `hr` — всех
сотрудников, `admin` — всё. Попытка прочитать чужую карточку, табель, отсутствия или
события возвращает `403`. Поля `oldSalary`/`newSalary` в событиях доступны только
`admin` и `hr`.

## Аутентификация

### `POST /auth/login`

Публичный эндпоинт.

**Запрос**

```json
{
  "email": "hr@hr.local",
  "password": "demo1234"
}
```

**Ответ `200`**

```json
{
  "token": "<jwt-or-opaque-token>",
  "user": {
    "id": "u2",
    "email": "hr@hr.local",
    "name": "Мария Смирнова",
    "role": "hr",
    "employeeId": "e002",
    "isActive": true,
    "mustChangePassword": false,
    "lastLoginAt": "2025-06-01T08:30:00.000Z"
  }
}
```

Если `mustChangePassword = true`, фронтенд после входа сразу ведёт на `/change-password`
и блокирует остальные разделы, пока пароль не будет заменён.

**Ошибки**

| Статус | Причина |
| --- | --- |
| `401` | Неверный email или пароль |
| `403` | Учётная запись заблокирована (`isActive = false`) |

### `GET /auth/me`

Возвращает текущего пользователя. Используется при перезагрузке приложения
для восстановления сессии.

**Ответ `200`** — объект `User` (как выше). **Ошибка:** `401` — токен отсутствует/истёк.

### `POST /auth/change-password`

Доступно любому авторизованному пользователю. Используется для добровольной смены пароля
и для обязательной смены временного пароля при первом входе.

```json
{
  "currentPassword": "<временный или текущий пароль>",
  "newPassword": "<не менее 8 символов>"
}
```

**Ответ `200`** — обновлённый `User` с `mustChangePassword: false`.
Сервер заменяет хеш пароля и завершает действие временного пароля.

**Ошибки**

| Статус | Причина |
| --- | --- |
| `400` | Текущий пароль неверен / новый короче 8 символов / совпадает с текущим |
| `401` | Нет или истёк токен |

## Сотрудники

### Модель `Employee`

```json
{
  "id": "e004",
  "personnelNumber": "EMP-004",
  "lastName": "Попова",
  "firstName": "Анна",
  "middleName": "Сергеевна",
  "birthDate": "1993-04-12",
  "gender": "female",
  "email": "a.popova@hr.local",
  "phone": "+7 900 000-00-04",
  "departmentId": "d2",
  "positionId": "p4",
  "managerId": "e003",
  "managerName": "Кузнецов Дмитрий",
  "hireDate": "2021-09-01",
  "dismissalDate": null,
  "status": "active",
  "employmentType": "full",
  "salary": 120000,
  "education": "МГУ, экономика",
  "notes": null
}
```

### `GET /employees`

Постраничный список с фильтрами и сортировкой.

**Query-параметры**

| Параметр | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `search` | string | — | Поиск по ФИО, email, табельному номеру, телефону |
| `departmentId` | string | — | Фильтр по подразделению |
| `positionId` | string | — | Фильтр по должности |
| `status` | enum | — | `active`, `probation`, `vacation`, `sick_leave`, `dismissed`; пустая строка = все |
| `projectId` | string | — | Только участники проекта |
| `page` | int | `1` | Страница (с 1) |
| `pageSize` | int | `20` | Размер страницы (мок ограничивает 500) |
| `sortBy` | enum | `name` | `name`, `hireDate`, `salary` |
| `sortDir` | enum | `asc` | `asc`, `desc` |

**Ответ `200`**

```json
{
  "items": [ /* Employee[] */ ],
  "total": 42,
  "page": 1,
  "pageSize": 20
}
```

> Поле `salary` возвращается `admin` и `hr` для всех сотрудников, а остальным ролям —
> только в собственной карточке (`employeeId` текущего пользователя). Оклад остальных
> сотрудников вырезается из ответа, а не только скрывается в интерфейсе.

### `GET /employees/{id}`

**Ответ `200`** — `Employee` (правило `salary` выше). `managerName` рассчитывает сервер:
сотрудник не имеет доступа к чужой карточке руководителя, но видит его ФИО в своей.
**Ошибка:** `404` — сотрудник не найден.

### `POST /employees`

**Тело запроса** (`EmployeePayload`): все поля из `Employee`, кроме `id`, `personnelNumber`,
`dismissalDate`, `notes`. Табельный номер генерирует бэкенд.

```json
{
  "lastName": "Иванов",
  "firstName": "Пётр",
  "middleName": "Алексеевич",
  "birthDate": "1990-01-20",
  "gender": "male",
  "email": "p.ivanov@hr.local",
  "phone": "+7 900 000-00-99",
  "departmentId": "d1",
  "positionId": "p2",
  "managerId": "e003",
  "hireDate": "2025-02-01",
  "status": "probation",
  "employmentType": "full",
  "salary": 150000,
  "education": "МГТУ"
}
```

**Ответ `201`** — созданный `Employee`.

### `PATCH /employees/{id}`

Частичное обновление **личных данных**: `lastName`, `firstName`, `middleName`,
`birthDate`, `gender`, `email`, `phone`, `employmentType`, `education`.

Подразделение, должность, руководитель, оклад, дата приёма и статус меняются только
кадровыми событиями (`POST /events`) — прямое изменение через `PATCH` возвращает `400`.
Email должен быть уникален. Если email учётной записи совпадал с email карточки,
он меняется вместе с карточкой; отдельный логин учётной записи не перезаписывается.
**Ответ `200`** — обновлённый `Employee`. **Ошибка:** `404`, `400` при занятом email.

### `DELETE /employees/{id}`

Удаление (в демо — физическое удаление из БД). Каскадно удаляются назначения,
задачи, отсутствия, события, табель, остатки отпусков и уведомления, связанные
с сотрудником; учётная запись блокируется. **Ответ `200`**: `{ "ok": true }`.
**Ошибка:** `404`.

## Орг-структура

### `GET /org/structure`

Дерево подразделений для экрана «Орг-структура». `admin`/`hr` получают всё дерево,
`manager` — своё подразделение с дочерними и подразделения, где он руководитель;
`employee` получает `403`.

**Ответ `200`**

```json
{
  "totalEmployees": 40,
  "roots": [
    {
      "id": "d1",
      "name": "Генеральный директор",
      "code": "GD",
      "parentId": null,
      "parentName": null,
      "head": { "id": "e001", "name": "Соколов Павел", "positionName": "Генеральный директор" },
      "directCount": 1,
      "totalCount": 40,
      "employees": [
        { "id": "e001", "name": "Соколов Павел", "positionName": "Генеральный директор" }
      ],
      "children": [ /* такие же узлы */ ]
    }
  ]
}
```

- `directCount` — активные сотрудники именно в этом подразделении;
- `totalCount` — с учётом дочерних;
- уволенные не входят;
- при цикле `parentId` ветка становится корнем, а не роняет страницу.

## Должности

### Модель `Position`

```json
{
  "id": "p15",
  "name": "Ведущий разработчик",
  "departmentId": "d5",
  "family": "Backend",
  "grade": 4,
  "salaryMin": 240000,
  "salaryMax": 360000
}
```

`departmentId` — подразделение, `family` — профессиональная ветка внутри подразделения,
`grade` — 1…4 (начальный → ведущий). Должность всегда принадлежит подразделению;
сотрудник может занимать только должность своего подразделения.

### `GET /positions` → `Position[]`
### `POST /positions` → `201`, тело `PositionPayload` (`name`, `departmentId`, `family`, `grade`, `salaryMin`, `salaryMax`)
### `PATCH /positions/{id}` → `200`

Вилку `salaryMin`/`salaryMax` может менять только `admin`; HR редактирует название,
подразделение, ветку и грейд. Занятую должность нельзя перенести в другое подразделение
без перевода сотрудников.

### `DELETE /positions/{id}` → `{ "ok": true }`; при занятой должности `400`

## Проекты

### Модель `Project`

```json
{
  "id": "pr1",
  "code": "CRM",
  "name": "Внедрение CRM",
  "description": "Новая CRM для отдела продаж",
  "status": "active",
  "startDate": "2025-01-15",
  "endDate": "2025-12-31",
  "managerId": "e006",
  "color": "#6366f1"
}
```

`status`: `planning` | `active` | `paused` | `completed`.
`color` — HEX-цвет для интерфейса.

### `GET /projects` → `Project[]`
### `GET /projects/{id}` → `Project` или `404`

- `employee` получает только проекты, где у него есть назначение.
- `manager` получает **все проекты** — как каталог. В интерфейсе по умолчанию
  открыт фильтр «Мои проекты», переключатель «Все проекты» показывает каталог.
- В чужом проекте manager видит только сводку (код, название, статус,
  руководитель, период). Команда, задачи и отчёт проекта скрыты до тех пор,
  пока он не станет руководителем проекта.
- `hr` / `admin` получают все проекты с полными деталями.
- В ответе есть `managerName` — ФИО руководителя, рассчитанное сервером. Это нужно
  каталогу: manager видит чужой проект, но не имеет права читать карточку его
  руководителя, поэтому имя приходит вместе с проектом.

### `POST /projects` → `201`, тело `ProjectPayload` (все поля, кроме `id`)

- `admin` / `hr` могут выбрать любого активного сотрудника руководителем.
- `manager` создаёт проект только с собой в роли руководителя; `managerId`
  принудительно устанавливается в его `employeeId`.
- Нельзя назначить уволенного сотрудника руководителем.

### `PATCH /projects/{id}` → `200`

- `admin` / `hr` могут менять любой проект и назначать руководителя.
- `manager` может менять только проект, где он руководитель. Он может **передать
  проект** другому активному сотруднику (`managerId`), после чего теряет доступ
  к управлению проектом. Снять руководителя (`null`) manager не может.
- Смена руководителя доступна только при праве `projects:manage-manager`
  (admin, HR и manager — в пределах своего проекта).

### `DELETE /projects/{id}` → `{ "ok": true }`; каскадно удаляет назначения и задачи проекта

Удаление доступно только `admin` / `hr`.

## Назначения на проекты

### Модель `Assignment`

```json
{
  "id": "a1",
  "projectId": "pr1",
  "employeeId": "e004",
  "projectRole": "Аналитик",
  "allocation": 50,
  "startDate": "2025-02-01",
  "endDate": null,
  "overloadReason": null
}
```

`allocation` — процент загрузки одного назначения (0–100). Суммарная **активная**
загрузка сотрудника по умолчанию не может превышать 100%. Проверяется не только дата
старта, а **пик за весь период** назначения: пересекающиеся будущие назначения тоже
учитываются. Только `admin` может разрешить перегруз до 150%, передав непустой
`overloadReason`; для остальных ролей `400`. Завершённые, будущие назначения
и назначения на завершённые проекты в текущую загрузку не входят.

### `GET /assignments`

| Параметр | Описание |
| --- | --- |
| `employeeId` | Только назначения сотрудника |
| `projectId` | Только назначения проекта |

**Ответ `200`** — `Assignment[]`.

### `POST /assignments` → `201`, тело `AssignmentPayload`
### `PATCH /assignments/{id}` → `200`
### `DELETE /assignments/{id}` → `{ "ok": true }`

## Задачи по проектам

Задача — отдельная сущность, привязанная к проекту и сотруднику. Создавать и удалять
задачи могут `admin` и `manager`; `hr` — только просматривать. Сотрудник видит свои задачи
и может отметить их выполненными или перенести на следующий рабочий день.

### Модель `ProjectTask`

```json
{
  "id": "t001",
  "projectId": "pr1",
  "employeeId": "e004",
  "title": "Подготовить макет личного кабинета",
  "description": "Собрать финальный макет главного экрана",
  "dueDate": "2025-06-10",
  "estimateHours": 6,
  "status": "todo",
  "createdById": "u3",
  "createdByName": "Дмитрий Кузнецов",
  "createdAt": "2025-06-07T08:00:00.000Z",
  "completedAt": null,
  "completionComment": null,
  "completedById": null,
  "completedByName": null,
  "completionHistory": [],
  "originalDueDate": "2025-06-09",
  "carryCount": 1,
  "carryHistory": [
    {
      "from": "2025-06-09",
      "to": "2025-06-10",
      "at": "2025-06-09T18:10:00.000Z"
    }
  ]
}
```

- `status`: `todo` | `done`.
- `dueDate` — текущая плановая дата; может сдвигаться при переносе.
- `originalDueDate` — исходный срок до переносов.
- `carryCount` / `carryHistory` — сколько раз и когда задача переносилась.
- `createdById` — `User.id` автора задачи (не `employeeId`).
- Задачу можно создать только сотруднику, назначенному на проект.
- По завершённому проекту (`status = completed`) новые задачи не создаются.

### `GET /tasks`

| Параметр | Описание |
| --- | --- |
| `employeeId` | Только задачи сотрудника (игнорируется для роли `employee`) |
| `projectId` | Только задачи проекта |
| `status` | `todo` / `done`; пустая строка = все |
| `mine` | `true` — только задачи текущего пользователя (по его `employeeId`) |

**Ответ `200`** — `ProjectTask[]`. Сортировка: сначала `todo`, затем по `dueDate`, затем
по `createdAt`. Роль `employee` всегда получает только собственные задачи; попытка
запросить чужой `employeeId` не расширяет выборку.

### `POST /tasks`

Только `admin` / `manager`.

```json
{
  "projectId": "pr1",
  "employeeId": "e004",
  "title": "Подготовить макет личного кабинета",
  "description": "Собрать финальный макет главного экрана",
  "dueDate": "2025-06-10",
  "estimateHours": 6
}
```

**Ответ `201`** — созданная задача со `status: "todo"`, `carryCount: 0`,
`carryHistory: []`, `originalDueDate = dueDate`, `createdAt` и автором из токена.

**Ошибки**

| Статус | Причина |
| --- | --- |
| `400` | Не заполнены обязательные поля, некорректная дата, оценка вне 0–1000 часов, проект завершён, сотрудник уволен или не назначен на проект |
| `403` | Роль не может создавать задачи |
| `404` | Проект или сотрудник не найден |

### `PATCH /tasks/{id}`

Частичное обновление.

```json
{
  "title": "Подготовить макет",
  "description": "Уточнённое описание",
  "dueDate": "2025-06-12",
  "estimateHours": 8,
  "status": "done",
  "completionComment": "Макет готов, согласован с дизайнером",
  "postpone": false
}
```

- `admin` / `manager` могут менять `title`, `description`, `dueDate`, `estimateHours`, `status`.
- `employee` может менять только `status` и `postpone` **у своей** задачи.
- `status = done` выставляет `completedAt`, `completedById`, `completedByName` и
  сохраняет `completionComment` — комментарий результата. Комментарий не обязателен,
  но рекомендуется; руководитель видит его в истории задачи.
- Возврат в `todo` очищает текущий результат, но добавляет запись в `completionHistory`.
- `postpone = true` переносит задачу на следующий **рабочий** день:
  пятница → понедельник, выходные пропускаются. Если задача уже просрочена,
  отсчёт идёт от сегодняшнего дня. При переносе увеличивается `carryCount`
  и добавляется запись в `carryHistory`. Выполненную задачу перенести нельзя (`400`).

**Ответ `200`** — обновлённая `ProjectTask`.

### `DELETE /tasks/{id}`

Только `admin` / `manager`. **Ответ `200`**: `{ "ok": true }`. **Ошибки:** `403`, `404`.

## Табель

### `GET /timesheet`

| Параметр | Обязателен | Описание |
| --- | --- | --- |
| `month` | нет | `YYYY-MM`, по умолчанию текущий месяц |
| `departmentId` | нет | Фильтр по подразделению |
| `employeeId` | нет | Только один сотрудник (используется для `/me`) |

**Ответ `200`**

```json
{
  "month": "2025-06",
  "normDays": 20,
  "normHours": 159,
  "rows": [
    {
      "employeeId": "e004",
      "days": [
        {
          "date": "2025-06-02",
          "code": "Я",
          "hours": 8,
          "isOverride": false
        }
      ],
      "normDays": 20,
      "workedDays": 19,
      "vacationDays": 0,
      "sickDays": 1,
      "tripDays": 0,
      "absentDays": 0,
      "totalHours": 152,
      "status": "draft"
    }
  ]
}
```

Правила кодов:

| Код | Значение | Часы |
| --- | --- | --- |
| `Я` | Рабочий день | 8 |
| `ОТ` | Отпуск | 0 |
| `Б` | Больничный | 0 |
| `К` | Командировка | 8 |
| `П` | Прогул | 0 |
| `Н` | Неоплачиваемый отпуск | 0 |
| `В` | Выходной | 0 |
| `—` | До приёма (день раньше `hireDate`) | 0 |

- Выходные (сб/вс) и нерабочие праздничные дни 2026–2027 годов заполняются `В` автоматически;
  в ячейке есть `dayType` (`weekend`, `holiday`, `transferred_off`, `shortened`) и
  `holidayName`. Праздники не входят в норму рабочих дней/часов.
- Дни раньше даты приёма сотрудника заполняются `—`, часы не начисляются.
- Согласованные отсутствия перекрывают рабочие дни соответствующим кодом:
  отпуск и учёба — `ОТ`, больничный — `Б`, командировка — `К` (8 часов),
  неоплачиваемый — `Н`. Заявки `pending`/`rejected` табель не меняют.
- При согласовании отсутствия ручные правки за эти даты удаляются — заявка важнее
  старой отметки.
- Ручные правки возвращаются с `isOverride: true`; `absenceId` указывается, если день
  сформирован отсутствием.
- `normDays` — число рабочих дней в месяце; `workedDays` — дни с `Я`; `totalHours` — сумма часов.

### `PATCH /timesheet/{employeeId}/{date}`

Ручная правка дня. `date` — `YYYY-MM-DD`.

```json
{ "code": "Я", "hours": 8 }
```

**Ответ `200`**: `{ "ok": true }`. Сервер сохраняет override для месяца `date.slice(0, 7)`.

Дата должна быть реальной датой `YYYY-MM-DD` (30 февраля отклоняется). Если дата
раньше `hireDate` сотрудника или позже `dismissalDate`, возвращается `400`; код `—`
вручную выставить нельзя. Если табель за этот месяц уже утверждён (`approved`), изменения
запрещены — сначала верните статус в `draft` или `submitted`.

### `PATCH /timesheet/{employeeId}/status`

```json
{ "month": "2025-06", "status": "approved" }
```

`status`: `draft` | `submitted` | `approved`. **Ответ `200`**: `{ "ok": true }`.

## Отсутствия

### Модель `Absence`

```json
{
  "id": "ab1",
  "employeeId": "e004",
  "type": "vacation",
  "startDate": "2025-06-10",
  "endDate": "2025-06-24",
  "days": 15,
  "workingDays": 11,
  "calendarDays": 15,
  "status": "pending",
  "reason": "Ежегодный отпуск",
  "createdAt": "2025-06-01T09:00:00.000Z",
  "approvedBy": null,
  "confirmedAt": null,
  "confirmedBy": null
}
```

`type`: `vacation` | `sick` | `business_trip` | `unpaid` | `study`.
`status`: `pending` | `approved` | `rejected`.
`days` — количество дней по типу отсутствия:
отпуск и отпуск без сохранения — календарные дни без нерабочих праздников;
больничный — календарные дни; командировка и учёба — рабочие дни по производственному
календарю. Дополнительно возвращаются `workingDays` и `calendarDays`.
`approvedBy` — `employeeId` согласовавшего.

### `GET /absences`

| Параметр | Описание |
| --- | --- |
| `employeeId` | Только отсутствия сотрудника |
| `status` | `pending`, `approved`, `rejected`; пустая строка = все |
| `month` | `YYYY-MM` — пересечение периода с месяцем |

**Ответ `200`** — `Absence[]`, сортировка по `startDate` (новые первыми).

### `POST /absences`

```json
{
  "employeeId": "e004",
  "type": "vacation",
  "startDate": "2025-06-10",
  "endDate": "2025-06-24",
  "reason": "Ежегодный отпуск"
}
```

**Ответ `201`** — созданная заявка со `status: "pending"`, рассчитанными `days` и `createdAt`.
**Ошибка `400`** — `endDate < startDate` или период пересекается с существующей заявкой
этого сотрудника в статусе `pending` / `approved`. Отклонённые заявки период не занимают.

### `PATCH /absences/{id}`

Частичное обновление полей `AbsencePayload`; при изменении дат пересчитывается `days`.
Период также проверяется на пересечение с другими заявками сотрудника (кроме самой
редактируемой). **Ответ `200`** — `Absence`; при пересечении — `400`.

### `GET /absences/{id}/task-handover`

Возвращает активные задачи сотрудника и кандидатов на переназначение.

```json
{
  "absenceId": "ab1",
  "tasks": [
    {
      "task": { "id": "t1", "title": "Подготовить макет", "projectId": "pr1" },
      "candidates": [
        { "employeeId": "e004", "employeeName": "Попова Анна", "projectRole": "Разработчик", "load": 70 }
      ]
    }
  ]
}
```

Кандидат должен быть участником того же проекта, не уволен, не иметь согласованного
отсутствия, пересекающегося с периодом, и иметь активную загрузку меньше 100%.

### `PATCH /absences/{id}/status`

```json
{
  "status": "approved",
  "taskDecisions": [
    { "taskId": "t1", "action": "keep", "comment": "Работает удалённо" },
    { "taskId": "t2", "action": "reassign", "employeeId": "e004" }
  ]
}
```

`taskDecisions` необязателен. Решения по задачам **не блокируют** согласование:
если решение не передано, задача остаётся у сотрудника. Если передан `reassign`,
сервер проверяет, что новый исполнитель — участник проекта, не уволен, не имеет
согласованного отсутствия и его загрузка меньше 100%. История решений пишется
в `absenceTaskDecisions` и аудит.

Для типа `sick` доступно только подтверждение: `status = "approved"` может отправить
только `hr` или `admin` (не руководитель). Повторное подтверждение допустимо, отклонение
и возврат в `pending` для больничного возвращают `400`. В ответе появляются
`confirmedAt` и `confirmedBy`.

Побочные эффекты при согласовании/отклонении:
- `approved` — `approvedBy` = текущий сотрудник, статус сотрудника синхронизируется
  (`vacation` / `sick_leave`, если период покрывает сегодня), а в кадровые события
  добавляется запись об отсутствии: `vacation`, `sick_leave`, `business_trip` или
  `unpaid_leave` (тип зависит от заявки). Повторное согласование не создаёт дубликат;
- `rejected` / `pending` — `approvedBy = null`, статус сотрудника возвращается к
  `active`/`probation`, связанное событие из ленты удаляется.

При изменении согласованной заявки (`PATCH /absences/{id}`) событие в ленте обновляется;
при удалении заявки (`DELETE`) оно удаляется вместе с ней.

При согласовании проверяется пересечение с другими **согласованными** отсутствиями
сотрудника; при пересечении возвращается `400`.

**Ответ `200`** — `Absence`.

### `DELETE /absences/{id}` → `{ "ok": true }`

## Кадровые события

### Модель `HrEvent`

```json
{
  "id": "ev1",
  "employeeId": "e004",
  "type": "promotion",
  "date": "2025-06-01",
  "title": "Повышение до старшего аналитика",
  "description": "По итогам аттестации",
  "fromDepartmentId": "d2",
  "toDepartmentId": null,
  "fromPositionId": "p4",
  "toPositionId": "p5",
  "oldSalary": 120000,
  "newSalary": 150000,
  "authorId": "e002",
  "absenceId": null
}
```

`type`: `hire` | `transfer` | `promotion` | `dismissal` | `salary_change` | `vacation` |
`sick_leave` | `business_trip` | `unpaid_leave`.

События типов `vacation`, `sick_leave`, `business_trip` и `unpaid_leave` создаются
автоматически при согласовании заявки на отсутствие и содержат `absenceId` — по нему
событие синхронизируется с заявкой (обновление дат, удаление). Вручную через
`POST /events` создаются только кадровые изменения (приём, перевод, повышение, оклад,
увольнение, отпуск).

### `GET /events`

| Параметр | Описание |
| --- | --- |
| `employeeId` | События сотрудника |
| `month` | `YYYY-MM` |
| `type` | Тип события |

**Ответ `200`** — `HrEvent[]`, сортировка по дате (новые первыми).

### `POST /events`

```json
{
  "employeeId": "e004",
  "type": "transfer",
  "date": "2025-07-01",
  "title": "Перевод в отдел аналитики",
  "description": "По согласованию руководителей",
  "toDepartmentId": "d3",
  "toPositionId": "p5",
  "newSalary": null
}
```

**Ответ `201`** — созданное событие.

Событие `hire` допускается только для уволенного сотрудника: это повторный приём.
Для действующего сотрудника возвращается `400`, дата приёма не перезаписывается.
`hr` не может создать `promotion` или `transfer` для самого себя — `403`.
Свою должность, подразделение и оклад HR меняет только через администратора.

Правила повышения (`type = "promotion"`):
- `toPositionId` обязателен и должен отличаться от текущей должности;
- новая должность — только из **того же подразделения** и **той же ветки**
  (`family`), с **большим грейдом**;
- для `hr` оклад автоматически устанавливается в `salaryMin` новой должности;
- `admin` может передать `newSalary`; если не передал — используется `salaryMin`;
- событие сохраняет старую/новую должность и старый/новый оклад.

Правила перевода (`type = "transfer"`):
- при смене подразделения `toPositionId` обязателен и должен относиться
  к новому подразделению;
- перевод без смены подразделения может менять только должность (в рамках
  текущего подразделения).

Побочные эффекты (выполняет бэкенд):

| Тип | Изменения сотрудника |
| --- | --- |
| `transfer` | `departmentId` ← `toDepartmentId`, `positionId` ← `toPositionId` (если переданы) |
| `promotion` | `positionId` ← `toPositionId`, `salary` ← `newSalary` |
| `salary_change` | `salary` ← `newSalary` |
| `dismissal` | `status = dismissed`, `dismissalDate = date` |
| `hire` | `status = active`, `hireDate = date` |

`fromDepartmentId`, `fromPositionId`, `oldSalary` заполняет сервер из текущей карточки.

## Дашборд

### `GET /dashboard?departmentId=...`

`departmentId` необязателен. Без параметра сервер применяет скоуп роли: `manager` —
своё подразделение, дочерние, подразделения где он руководитель, и команды своих
проектов; `admin`/`hr` — все сотрудники. С параметром — дополнительный фильтр по
точному подразделению в пределах скоупа. Все метрики считаются по одной области.

**Ответ `200`**

```json
{
  "headcount": 38,
  "probation": 3,
  "hiredThisMonth": 2,
  "dismissedThisMonth": 1,
  "activeProjects": 6,
  "avgUtilization": 87,
  "absentToday": 2,
  "pendingAbsences": 4,
  "byDepartment": [{ "name": "ИТ-департамент", "count": 14 }],
  "dynamics": [{ "month": "2025-01", "hired": 2, "dismissed": 1 }],
  "teamByProject": [{ "name": "Внедрение CRM", "count": 8 }],
  "birthdays": [{ "employeeId": "e004", "date": "2025-06-12", "daysLeft": 5 }],
  "recentEvents": [ /* HrEvent[] */ ]
}
```

- `headcount` — активные (не уволенные) сотрудники в скоупе.
- `avgUtilization` — средняя сумма назначений на сотрудника, %.
- `byDepartment` — распределение численности.
- `dynamics` — последние 6 месяцев приёма/увольнений.
- `teamByProject` — top-6 активных проектов по числу уникальных участников.
- `birthdays` — ближайшие 30 дней. Для роли `manager` поле всегда пустое:
  дни рождения других подразделений менеджеру не показываются.

## Пользователи

Учётная запись (`User`) — отдельная сущность, необязательно связанная с карточкой
сотрудника (`Employee`) отношением 1:1. Сотрудник может существовать без учётной записи:
тогда вход в систему под ним невозможен.

Просмотр и изменение списка пользователей — только `admin`. Создавать учётные записи могут
`admin` (любая роль) и `hr` (только роль `employee`).

### Модель `User`

```json
{
  "id": "u2",
  "email": "hr@hr.local",
  "name": "Мария Смирнова",
  "role": "hr",
  "employeeId": "e002",
  "isActive": true,
  "mustChangePassword": false,
  "lastLoginAt": "2025-06-01T08:30:00.000Z"
}
```

- `email` — уникален без учёта регистра.
- `employeeId` — `null`, если учётная запись не привязана к сотруднику.
- `mustChangePassword` — `true` после выдачи временного пароля; сбрасывается после
  `POST /auth/change-password`.
- `lastLoginAt` — время последнего успешного входа, `null` до первого входа.

### `GET /users` → `User[]`

Только `admin`.

### `GET /users/by-employee/{employeeId}`

Возвращает `User` или `null`, если у сотрудника нет учётной записи. Доступно `admin` и `hr`.
Используется в карточке сотрудника, чтобы показать и создать доступ.

### `POST /users`

Создаёт учётную запись и возвращает временный пароль **один раз**.

```json
{
  "email": "p.ivanov@hr.local",
  "name": "Иванов Пётр",
  "role": "employee",
  "employeeId": "e043"
}
```

**Ответ `201`**

```json
{
  "user": {
    "id": "u6",
    "email": "p.ivanov@hr.local",
    "name": "Иванов Пётр",
    "role": "employee",
    "employeeId": "e043",
    "isActive": true,
    "mustChangePassword": true,
    "lastLoginAt": null
  },
  "temporaryPassword": "K7mQ2xR9pL4a"
}
```

Правила сервера:

- `email` обязателен, уникален и нормализуется (trim + lower case);
- `employeeId`, если передан, должен существовать; у сотрудника не должно быть другой учётной записи;
- уволенному сотруднику (`status = dismissed`) доступ не создаётся;
- `hr` может передать только `role = employee`, иначе `403`;
- пароль генерирует сервер, в БД хранится только хеш (Argon2id/bcrypt);
- `mustChangePassword = true`, `isActive = true`, `lastLoginAt = null`;
- создание пишется в аудит.

**Ошибки**

| Статус | Причина |
| --- | --- |
| `400` | Некорректный/занятый email, у сотрудника уже есть доступ, сотрудник уволен |
| `401` | Нет или истёк токен |
| `403` | Недостаточно прав или HR пытается назначить не-`employee` роль |
| `404` | Передан несуществующий `employeeId` |

### `PATCH /users/{id}`

Только `admin`.

```json
{ "role": "manager", "isActive": false }
```

Менять можно только `role` и `isActive`. **Ответ `200`** — `User`. **Ошибка:** `404`.

Сервер обязан запрещать блокировку собственной учётной записи (`400`), даже если кнопка
в интерфейсе уже заблокирована. При увольнении сотрудника (`POST /events` с типом
`dismissal` или `PATCH /employees/{id}` со статусом `dismissed`) связанная учётная запись
блокируется автоматически.

## Рекомендации по реализации на FastAPI

1. **Структура**: `app/main.py`, `app/api/v1/*.py` (роутеры по доменам), `app/models`, `app/schemas`
   (Pydantic v2), `app/core/security.py`, `app/services/*`.
2. **Префикс**: подключите все роутеры с `prefix="/api/v1"`.
3. **Аутентификация**: OAuth2 Password Bearer или простой JWT (`python-jose`/`pyjwt`).
   На `401` возвращайте `{"detail": "Сессия истекла"}` — фронтенд разлогинится.
4. **CORS**: при отдельном origin (`VITE_API_URL=http://localhost:8000/api/v1`) разрешите
   `http://localhost:5173` и production-домен, заголовки `Authorization`, `Content-Type`.
5. **Ошибки**: используйте `HTTPException(status_code=..., detail="...")`.
   Для ошибок валидации FastAPI по умолчанию отдаёт `detail: []` — фронтенд покажет
   «Проверьте заполнение формы». Если нужны сообщения по полям, верните `fields`.
6. **Даты/деньги**: Pydantic `date`, `int` для рублей; сериализация дат — ISO (`YYYY-MM-DD`).
7. **Пагинация**: придерживайтесь формата `Paginated<T>` (`items`, `total`, `page`, `pageSize`).
8. **Порядок сортировки**: `sortBy`/`sortDir` из query-параметров; по умолчанию — по ФИО.
9. **Аудит**: пишите запись в журнал на каждое изменение (создание/обновление/удаление,
   смену статуса, вход).
10. **Мок-данные**: исходный набор сотрудников/справочников — в `src/mocks/data.ts`,
    его удобно использовать как seed для БД.
11. **Проверка контракта**: после подключения FastAPI прогоните сценарии всех четырёх ролей;
    регрессия контракта ловится по `src/shared/types.ts` и `src/shared/api/index.ts`.
12. **Временные пароли**: генерируйте криптостойкий пароль на сервере, храните только хеш,
    возвращайте открытый пароль единственным ответом `POST /users` и требуйте смену через
    `mustChangePassword`. Не логируйте временный пароль и не сохраняйте его в БД.
