## 3. Найденные и исправленные проблемы

### 3.1. Mass assignment в API

**Проблема:** `Object.assign(entity, body)` и `{ ...body }` позволяли клиенту
подменить `id`, служебные поля и статусы в обход сценария.

**Исправление:** в `src/mocks/handlers.ts` добавлен `pickFields()` и белые списки полей
для сотрудников, подразделений, должностей, проектов, назначений, отсутствий и
пользователей. Теперь API принимает только те поля, которые разрешено менять.

### 3.2. Самостоятельное согласование отсутствия

**Проблема:** сотрудник с собственной заявкой в статусе `pending` мог отправить
`PATCH /absences/:id` с `{ status: 'approved' }` или `{ employeeId: '...' }`.
Проверка прав пропускала запрос, после чего `Object.assign` применял подмену.

**Исправление:**

- `PATCH /absences/:id` применяет только `type`, `startDate`, `endDate`, `reason`;
- `status`, `employeeId`, `id`, `days`, `createdAt`, `approvedBy` игнорируются;
- тип отсутствия валидируется тем же списком, что и при создании;
- добавлен тест «не позволяет подменить статус или сотрудника через PATCH заявки».

### 3.3. Падение `can()` на неизвестной роли

**Проблема:** `access[role].includes(action)` падал, если в `hr-auth` сохранилась роль
из старой версии схемы. Это тот же класс ошибки, что и `.tone`.

**Исправление:**

- `src/shared/lib/permissions.ts` — `can()` возвращает `false`, если роли нет в матрице;
- `src/shared/api/index.ts` — `normalizeUser()` отбрасывает невалидную роль;
- добавлен тест `src/shared/lib/permissions.test.ts`.

### 3.4. Потеря всей демо-БД при пустом списке сотрудников

**Проблема:** `loadDb()` пересоздавал базу, если `employees.length === 0`. После удаления
последнего сотрудника следующая загрузка молча заменяла все данные сидом.

**Исправление:** база пересоздаётся только при структурно неверном ответе
(`parsed` отсутствует или `employees` — не массив). Добавлен тест
«keeps an intentionally empty employee list instead of reseeding».

### 3.5. Невалидные кадровые события

**Проблема:** `POST /events` не проверял тип, дату и название. Событие без даты ломало
сортировку `GET /events`, а событие приёма/увольнения портило `hireDate`/`dismissalDate`.

**Исправление:**

- проверка типа по `HR_EVENT_TYPES`;
- проверка `dayjs(body.date).isValid()`;
- проверка непустого названия;
- сортировки событий, отсутствий и сотрудников переведены на `String(value ?? '')`;
- аналогичная защита добавлена в `sortTasks()`.

### 3.6. Роли и блокировка пользователей

**Проблема:** API пользователей мог сохранить роль вне объединения и `isActive: "false"`
(строка, которая truthy). Это ломало навигацию и проверку входа.

**Исправление:**

- роль проверяется по `ROLES`;
- `isActive` должен быть boolean;
- `PATCH /users/:id` применяет только `role` и `isActive`.

### 3.7. Дублирование перечислений

**Проблема:** списки статусов и типов были продублированы в миграции, API и формах.
Один пропущенный список уже приводил к рассинхронизации.

**Исправление:** добавлен `src/shared/lib/enums.ts` — единый источник значений:

- роли, статусы сотрудников, проектов, задач, отсутствий, табеля, зарплаты;
- типы занятости, пола, кадровых событий.

Миграция, API и формы (`absence-form`, `employee-form`) используют эти списки.
`enums.ts` связан с типами через `satisfies`, поэтому невалидное значение не соберётся.

### 3.8. Небезопасные подписи ролей и типов

**Проблема:** `roleLabels`, `employmentTypeLabels`, `genderLabels` были обычными объектами
и могли отрендерить пустоту или `undefined` на старых данных.

**Исправление:** добавлен `withStringFallback()`; неизвестное значение показывается как
`Неизвестно (значение)`. `syncAbsenceEvent()` дополнительно не создаёт событие, если тип
отсутствия неизвестен.

### 3.9. Дублирование тестовой инфраструктуры

**Проблема:** класс `MemoryStorage` был скопирован в двух тестах.

**Исправление:** вынесен в `src/test/memory-storage.ts`, оба теста используют его.

## 5. Инструменты и ограничения

- **`crapper`, `dryer`, `mutator`** в проекте не установлены. Гейты не запускались;
  вместо них использованы существующие тесты и проверка сборки. Это отмечено как
  ограничение, а не как пройденная проверка.
- Проект **не является git-репозиторием**, поэтому commit/push не выполнялись.
  Контрольная точка — zip-бэкап, указанный в начале.
- Даты в старых записях (`hireDate`, даты отсутствий, `event.date`) пока не
  нормализуются в миграции. Падения устранены защитой сортировок, но в старых данных
  возможны `Invalid Date`/`NaN`. Это следующий кандидат на исправление.
- Демо по-прежнему хранит токен и данные в `localStorage`. Для реальных ПДн это
  недопустимо; вопрос решается на этапе бэкенда и защищённых cookie.

## 8. Уточнение прав HR

Дата: 18.11.2026, после продуктового ревью ролей.

Изменения:

- HR больше не удаляет сотрудников; физическое удаление — только admin.
- HR не увольняет и не восстанавливает сотрудников; статус `dismissed` меняет admin.
- HR не создаёт заявки на отсутствие за других; сотрудник создаёт свою заявку сам.
  HR только согласовывает/отклоняет (кроме собственной).
- HR не создаёт событие увольнения; оно доступно только admin.
- Табель разделён на `timesheet:edit` и `timesheet:approve`: HR смотрит и утверждает,
  но не меняет отметки.
- HR видит зарплату только для чтения; расчёт и премии — admin.
- Оклад устанавливает только admin; HR и руководитель видят его только для чтения.
  HR не может создать событие изменения оклада.
- Добавлены проверки удаления подразделений/должностей, к которым привязаны сотрудники.
- Добавлена иерархия согласования отсутствий: HR подтверждает только администратор.
- Увольнение стало мягким архивом: назначения закрываются, заявки на согласовании
  отклоняются, аккаунт блокируется; история сохраняется. Восстановление возвращает доступ.
- При увольнении и физическом удалении показывается блок активных задач с выбором
  нового исполнителя; если задач нет, блок не отображается.
- Свой табель и свою заявку на отсутствие может утвердить только администратор.
- Согласованные заявки нельзя редактировать и удалять напрямую: только вернуть
  на согласование или отклонить.
- История табеля уволенного доступна в его карточке, но не в общем табеле.
- Текущая загрузка/размер команды проекта не учитывают закрытые назначения.
- Матрица и правила вынесены в `docs/ROLES.md`, README обновлён.
