# Бэкенд: стек, архитектура и план реализации

> **Статус:** проектная документация. Бэкенд ещё не реализован — сейчас фронтенд работает
> на MSW-моках. Контракт эндпоинтов описан в [`docs/API.md`](API.md).
>
> Документ отвечает на вопросы: что делать, почему выбран именно этот стек, какие
> альтернативы отклонены и как понять, что бэкенд готов к защите.

---

## 1. Цель бэкенда

Для бакалаврского диплома по ИСиТ бэкенд должен закрыть три вещи:

1. **Хранение данных** — реальная БД со схемой, ограничениями целостности и миграциями.
2. **Бизнес-логика на сервере** — правила нельзя обойти через DevTools или прямые запросы.
3. **Промышленные практики** — авторизация, транзакции, тесты, развёртывание, документация.

Фронтенд уже готов и ожидает REST API из `docs/API.md`. Задача бэкенда — реализовать этот
контракт, а не переписывать клиент.

## 2. Рекомендуемый стек

| Компонент | Выбор | Почему именно это | Почему не альтернатива |
| --- | --- | --- | --- |
| Язык и фреймворк | **Python 3.12 + FastAPI** | Быстрая соло-разработка, Pydantic-валидация, автоматический OpenAPI/Swagger, async, минимум boilerplate. Хорошо ложится на ИСиТ и задачи анализа данных | Django/DRF — мощно, но тяжелее и навязывает admin/templates; Flask — нет встроенной валидации и OpenAPI; Node/Nest — допустимо, но тогда два языка; Spring/ASP.NET — многословно для одного разработчика |
| СУБД | **PostgreSQL 16** | Домен строго реляционный. Нужны FK, CHECK, уникальные индексы, транзакции, агрегаты для отчётов, `JSONB` для аудита и `daterange` для отпусков | SQLite — только для тестов/прототипа: слабая конкурентность и миграции; MySQL — возможен, но в Postgres сильнее ограничения, JSONB и оконные функции; MongoDB — данные связаны, нужна целостность, а не документы |
| ORM | **SQLAlchemy 2.0** | Явные модели, связи, контроль транзакций, async, промышленный стандарт. Хорошо видно на ER-диаграмме | Чистый SQL — больше кода и ошибок; Django ORM — только вместе с Django; Tortoise — меньше экосистема |
| Миграции | **Alembic** | Схема будет меняться по ходу диплома. Миграции дают воспроизводимость, историю изменений и откат | `create_all()` — не годится для защиты: нет истории и управляемого развёртывания |
| Авторизация | **JWT (access + refresh), Argon2id/bcrypt** | Фронтенд уже отправляет `Authorization: Bearer`. JWT не требует cookie-хранилища и упрощает CORS для SPA | Сессии на cookie — сложнее с отдельным origin и CSRF; пароли в открытом виде — дисквалификация; роль с клиента — дыра в доступе |
| Архитектура | **Модульный монолит, слои** | Для одного разработчика это оптимум: транзакции в одной БД, простой деплой, понятная защита. Слои `router → service → repository → model` дают тестируемость | Микросервисы — оверинжиниринг: сеть, eventual consistency, observability, больше времени на инфраструктуру, чем на систему |
| API | **REST + `/api/v1` + OpenAPI** | Контракт уже описан, CRUD-характер, легко кэшировать и тестировать. Swagger — бесплатный плюс на защите | GraphQL — избыточен для CRUD и усложняет авторизацию; gRPC — не для браузера без прослойки |
| Тесты | **pytest + httpx + PostgreSQL в Docker** | Проверяют бизнес-правила и API на реальной БД, а не на моках. Это доказательство работоспособности | Только Postman-коллекция — не регрессия и не воспроизводимость |
| Развёртывание | **Docker Compose + Nginx** | `docker compose up` поднимает frontend, backend и БД на любом ноутбуке | Kubernetes — не нужен для одного хоста; ручная установка — риск «у меня не запускается» |
| Документация | **OpenAPI + ER + README + ТЗ** | Комиссия оценивает не только код, но и проектную часть | Только комментарии в коде — недостаточно |

> Если на кафедре требуют Java или C# — берите **Spring Boot** или **ASP.NET Core**.
> Принципы те же: слои, JWT, PostgreSQL, миграции, тесты, Docker. Меняется обоснование,
> архитектура остаётся.

## 3. Архитектура

```
┌────────────────────┐        HTTPS/JSON         ┌─────────────────────────┐
│  React SPA (Vite)  │ ────────────────────────> │  FastAPI (Uvicorn)      │
│  axios, Bearer JWT │ <──────────────────────── │  /api/v1, OpenAPI       │
└────────────────────┘                           └───────────┬─────────────┘
                                                             │ SQLAlchemy
                                                             ▼
                                                 ┌─────────────────────────┐
                                                 │  PostgreSQL 16          │
                                                 │  миграции Alembic       │
                                                 └─────────────────────────┘
```

### Слои

```
app/
├── main.py                 # создание приложения, CORS, роутеры, healthcheck
├── core/
│   ├── config.py           # настройки из .env (pydantic-settings)
│   ├── security.py         # JWT, хеширование паролей
│   └── deps.py             # get_db, get_current_user, require_role
├── api/v1/
│   ├── auth.py
│   ├── employees.py
│   ├── departments.py
│   ├── positions.py
│   ├── projects.py
│   ├── assignments.py
│   ├── timesheet.py
│   ├── absences.py
│   ├── events.py
│   ├── dashboard.py
│   ├── users.py
│   └── audit.py
├── models/                 # SQLAlchemy-модели
├── schemas/                # Pydantic v2: request/response
├── services/               # бизнес-логика, транзакции, расчёты
├── repositories/           # запросы к БД (по желанию, при разрастании)
└── db/
    ├── base.py
    └── seed.py             # демо-данные из src/mocks/data.ts
```

**Почему так:** роутеры отвечают только за HTTP и валидацию, сервисы — за правила,
модели — за хранение. Это позволяет тестировать бизнес-логику без HTTP и не дублировать
код между эндпоинтами. Микросервисы не нужны: одна БД, один узел, транзакции проще.

### Как переносить правила из мока

Мок уже разделён по тем же слоям, чтобы FastAPI не приходилось «выковыривать» правила
из обработчиков:

| Мок | FastAPI | Правило переноса |
| --- | --- | --- |
| `src/mocks/handlers/*.ts` | `app/api/v1/*.py` | Только HTTP: токен, роль, разбор тела, вызов сервиса, ответ |
| `src/mocks/domain/*.ts` | `app/services/*.py` | Бизнес-правила: доступ, отпуска, загрузка, увольнение, повышение |
| `src/mocks/domain/result.ts` | `HTTPException` | `RuleError.status` уже соответствует 400/403/404 из контракта |
| `src/mocks/domain/fields.ts` | Pydantic-схемы | Белые списки полей — это будущие `*Payload`-модели |
| `Db` в аргументах | SQLAlchemy-сессия | В Python функции принимают сессию и репозитории, а не весь `Db` |
| `src/mocks/*.test.ts` | `tests/test_*.py` | Сценарии те же: роли, пересечения, границы периодов |

Практическое правило: **новую бизнес-проверку не писать в `handlers/`**. Сначала чистая
функция в `domain/` с `RuleResult`, затем тонкий вызов из роутера. Тогда при переходе
на FastAPI функция переписывается один раз, а не ищется по всем обработчикам.

## 4. Модель данных

Минимальный набор таблиц:

```
users ──1:1── employees
departments ──< employees >── positions
employees ──< assignments >── projects
employees ──< project_tasks >── projects
employees ──< absences
employees ──< hr_events
employees ──< timesheet_entries
audit_log
```

### Ключевые таблицы

| Таблица | Назначение | Важные поля и ограничения |
| --- | --- | --- |
| `users` | Учётные записи | `email UNIQUE`, `password_hash`, `role`, `employee_id UNIQUE`, `is_active`, `must_change_password`, `last_login_at` |
| `employees` | Карточки сотрудников | `personnel_number UNIQUE`, `email UNIQUE`, `department_id`, `position_id`, `status`, `salary CHECK >= 0` |
| `departments` | Подразделения | `code UNIQUE`, `parent_id` (самоссылка), `head_id` |
| `positions` | Должности | `name`, `department_id`, `family`, `grade`, `salary_min`, `salary_max`, `CHECK salary_min <= salary_max`, `CHECK grade BETWEEN 1 AND 4` |
| `projects` | Проекты | `code UNIQUE`, `status`, `start_date`, `end_date`, `CHECK end_date >= start_date` |
| `assignments` | Назначения на проекты | `employee_id`, `project_id`, `allocation CHECK 0..100`, `UNIQUE(employee_id, project_id, start_date)` |
| `project_tasks` | Задачи по проектам | `project_id`, `employee_id`, `title`, `due_date`, `original_due_date`, `status`, `estimate_hours`, `created_by`, `created_at`, `completed_at`, `carry_count`, `carry_history JSONB` |
| `absences` | Отпуска/больничные | `type`, `status`, `start_date`, `end_date`, `CHECK end_date >= start_date` |
| `hr_events` | Кадровые события | `type`, `date`, `from/to department/position`, `old/new salary` |
| `timesheet_entries` | Табель | `employee_id`, `date`, `code`, `hours`, `is_override`, `UNIQUE(employee_id, date)` |
| `audit_log` | Журнал действий | `at`, `user_id`, `action`, `entity`, `entity_id`, `details JSONB`, append-only |

### Ограничения, которые стоит показать в записке

- `UNIQUE(employee_id, date)` в табеле.
- `CHECK(allocation BETWEEN 0 AND 100)`, `CHECK(salary >= 0)`, `CHECK(end_date >= start_date)`.
- FK с `ON DELETE RESTRICT` для справочников и `ON DELETE CASCADE` для дочерних записей.
- Индексы: `employees(department_id)`, `employees(status)`, `absences(employee_id, start_date, end_date)`, `timesheet_entries(employee_id, date)`, `project_tasks(employee_id, status, due_date)`, `project_tasks(project_id)`.
- `project_tasks.employee_id` должен ссылаться на существующее назначение `(project_id, employee_id)`; проверку удобно выполнять в сервисе, чтобы не дублировать составной FK.
- Запрет пересекающихся согласованных отпусков:
  `EXCLUDE USING gist (employee_id WITH =, daterange(start_date, end_date, '[]') WITH &&)`
  (нужно расширение `btree_gist`).
- `audit_log` не обновляется и не удаляется через API.

Почему Postgres: это не «просто таблицы», а **спроектированная ИС** с декларативной
целостностью. Комиссия увидит ER-модель, нормализацию и осмысленные ограничения.

## 5. Аутентификация и разграничение доступа

### Схема

1. `POST /auth/login` — проверка email/пароля, выдача access-токена (30–60 мин) и refresh-токена.
2. `GET /auth/me` — текущий пользователь по токену.
3. Пароли — Argon2id (или bcrypt), никогда не в открытом виде.
4. Роль и `employee_id` берутся **из токена/БД**, а не из тела запроса.
5. Зависимость `require_role(...)` на каждом роутере.
6. `401` — невалидный/истёкший токен; `403` — недостаточно прав.
7. Rate limit на `/auth/login` (например, `slowapi`).

### Учётные записи и временные пароли

1. `Employee` и `User` — разные сущности. У сотрудника может не быть учётной записи;
   тогда вход невозможен, но кадровая карточка существует.
2. `POST /users` создаёт `User` по явному запросу. Сервер генерирует временный пароль
   криптостойким ГПСЧ, сохраняет **только хеш** и возвращает открытый пароль один раз.
3. В ответе `User.mustChangePassword = true`. Пока флаг не сброшен, `POST /auth/change-password`
   — единственный доменный эндпоинт, который должен выполняться; остальные можно отклонять
   с `403`, а фронтенд и так редиректит на `/change-password`.
4. `POST /auth/change-password` проверяет текущий пароль, валидирует длину нового (≥ 8),
   заменяет `password_hash`, ставит `must_change_password = false` и пишет аудит.
5. При увольнении (`POST /events` с `dismissal` или `PATCH /employees/{id}` со статусом
   `dismissed`) связанная учётная запись блокируется: `is_active = false`.
6. Сброс пароля администратором (если появится) должен снова выдавать временный пароль,
   ставить `must_change_password = true` и отзывать активные refresh-сессии пользователя.

### Скоупинг

- `admin` — всё.
- `hr` — всё, кроме управления пользователями и журнала (по матрице из `docs/API.md`).
- `manager` — чтение сотрудников и данных своего подразделения; проекты, назначения
  и задачи — только там, где он `project.manager_id`.
  В область чтения также входят команды его проектов (для списков, табеля, отсутствий),
  но согласование табеля и заявок — только подразделение с дочерними и руководимые отделы.
- `employee` — только своя карточка, свои отсутствия, табель и загрузка.

Любая попытка прочитать чужое — `403`, а не «пустой список». Это важнее, чем красивые
кнопки: проверяется прямой запрос через curl.

## 6. Бизнес-логика на сервере

### Табель

- Расчёт рабочих дней и кодов `Я/ОТ/Б/К/П/Н/В/—` — на сервере.
- Выходные заполняются автоматически.
- Дни раньше `hire_date` заполняются `—` (до приёма), часы и оплата не начисляются.
- Согласованные отсутствия перекрывают рабочие дни.
- Коды отсутствий: отпуск и учёба — `ОТ`, больничный — `Б`, командировка — `К` (8 ч),
  неоплачиваемый — `Н`. Заявки в статусе `pending`/`rejected` табель не меняют.
- При согласовании отсутствия ручные правки (`overrides`) за эти даты удаляются:
  согласованная заявка важнее старой ручной отметки.
- Ручные правки — отдельная таблица/флаг `is_override`.
- `PATCH /timesheet/{employeeId}/{date}` принимает только код и часы; даты раньше
  `hire_date`, даты после `dismissal_date` и код `—` отклоняются с `400`.
- Ручные правки доступны `admin` и `hr`. Каждое изменение пишется в аудит
  с сотрудником, датой, кодом и часами.
- После утверждения табеля (`status = approved`) правки запрещены всем, кроме
  `admin`: аварийная правка администратора разрешена и помечается в аудите
  «правка после утверждения». HR и manager должны сначала вернуть статус
  в `draft`/`submitted`.

### Отсутствия

- `days` считается по рабочим дням на сервере.
- Согласование — **одна транзакция**: обновить заявку, статус сотрудника, табель, аудит.
- Запрет `end_date < start_date` и пересечений с заявками в статусах `pending`/`approved`
  (при согласовании — с уже утверждёнными отсутствиями).
- Согласование `sick`, `business_trip` и `vacation` не блокируется активными задачами:
  по каждой задаче передаётся решение `keep` или `reassign`. Для `reassign` проверяются
  проект, статус сотрудника, отсутствие пересекающегося согласованного отсутствия
  и загрузка меньше 100%.
- Отклонение возвращает статус сотрудника к `active`/`probation`.

### Проекты и команда

- `admin`/`hr` создают проекты и назначают любого активного руководителя.
- `manager` создаёт проект только с собой в роли руководителя.
- `manager` редактирует и управляет командой только своих проектов.
- `manager` может передать свой проект другому активному сотруднику (`manager_id`)
  и после передачи теряет доступ к управлению; снять руководителя (`null`) не может.
- `manager` не может удалять проект.
- Удаление проекта — `admin`/`hr`, каскадно удаляются назначения и задачи.
- В `PATCH /projects/{id}` смена `manager_id` требует права `projects:manage-manager`.

### Кадровые события

- При переводе/повышении/увольнении сервер сам обновляет карточку сотрудника.
- `from_*` и `old_salary` заполняются из текущей карточки, а не приходят от клиента.
- `promotion` требует `to_position_id`, отличный от текущей должности.
- Повышение — только в том же подразделении и той же ветке (`positions.family`),
  с большим грейдом; иначе `400`. Смена подразделения — только через `transfer`,
  при этом целевая должность должна принадлежать новому подразделению.
- Для `hr` новый оклад при повышении = `positions.salary_min`; `admin` может передать
  свой оклад, иначе тоже используется `salary_min`.
- Всё — в одной транзакции с записью события и аудита.
- `GET /events` и `recentEvents` дашборда ограничены скоупом чтения: `admin`/`hr` видят
  всю компанию, `manager` — свою область и команды своих проектов (не общую ленту),
  `employee` — только свои события.
- `recentEvents` сортируются по времени создания (новые сверху), `GET /events` — по дате
  события. Оклад (`old_salary`/`new_salary`) вырезается для всех, кроме `admin`/`hr`
  и самого сотрудника.

### Задачи по проектам

- Создавать и удалять задачи могут `admin` и `manager`; `hr` — просмотр.
- `manager` может создавать, менять и удалять задачи только в своих проектах
  (`projects.manager_id = current_employee_id`).
- Сотрудник может менять только `status` и `postpone` у собственной задачи.
- Задачу можно создать только сотруднику, назначенному на проект; по завершённому
  проекту — нельзя.
- `postpone` переносит срок на следующий рабочий день (пятница → понедельник,
  выходные пропускаются). Если задача просрочена, отсчёт идёт от сегодня.
- Перенос увеличивает `carry_count` и добавляет запись в `carry_history`:
  `{ "from": "...", "to": "...", "at": "..." }`.
- `status = done` выставляет `completed_at`; возврат в `todo` очищает его.
- Все изменения пишутся в аудит с `entity = task`.

### Отчёты и дашборд

- Агрегаты считаются SQL-запросами, а не выгрузкой всех строк в браузер.
- Индексы под фильтры и периоды.
- Пагинация — формат `Paginated<T>` из `src/shared/types.ts`.

### Аудит

- Пишется на каждое изменение: создание, обновление, удаление, смену статуса, вход.
- Поля: кто, когда, действие, объект, `before/after` в `JSONB`, request id.
- Append-only: API не позволяет изменить или удалить запись.

## 7. Безопасность и правовой контекст

Для HR-данных стоит явно указать в пояснительной записке:

- **152-ФЗ** — персональные данные: минимизация, разграничение доступа, логирование,
  хранение секретов вне репозитория.
- Пароли — только хеши (Argon2id/bcrypt), не MD5/SHA.
- Временный пароль показывается один раз, не логируется и не хранится в открытом виде;
  после первого входа обязательна смена (`must_change_password`).
- CORS — whitelist конкретных origin, не `*` с credentials.
- Rate limit на логин и чувствительные операции.
- Валидация всех входных данных Pydantic-схемами, отдельные request/response модели.
- Отдельный пользователь БД с минимальными правами.
- HTTPS и секреты через переменные окружения.
- Запрет mass assignment: клиент не присылает `id`, `role`, `personnel_number` и служебные поля.
- Аудит действий и запрет удаления audit-записей.

## 8. Тестирование

Пирамида:

| Уровень | Инструмент | Что проверять |
| --- | --- | --- |
| Unit | pytest | Расчёт дней, коды табеля, валидаторы |
| Integration | pytest + httpx + PostgreSQL | Эндпоинты, права ролей, транзакции, ограничения БД |
| Contract | OpenAPI-схема | Соответствие ответов `docs/API.md` и `src/shared/types.ts` |
| E2E | Playwright | Вход, CRUD сотрудника, согласование отпуска, табель |

Почему не только Postman: коллекция не даёт регрессии, не запускается в CI и не
доказывает воспроизводимость. Почему реальная БД, а не SQLite в тестах: нужно проверять
FK, CHECK, `EXCLUDE`, транзакции и конкурентность — то, чем Postgres и ценен.

Минимальный набор тестов к защите:

- вход с верным/неверным паролем, заблокированный пользователь;
- создание сотрудника без учётной записи и с временным паролем;
- обязательная смена пароля при первом входе и запрет остальных действий до неё;
- запрет повторной учётной записи для того же сотрудника и назначения роли выше прав HR;
- доступ ролей к каждому разделу (включая `403` на чужие данные);
- создание/редактирование/удаление сотрудника и справочников;
- запрет удаления занятой должности и подразделения с сотрудниками;
- согласование отпуска: статус заявки, статус сотрудника, табель, аудит;
- задачи: создание только для участника проекта, запрет по завершённому проекту,
  права HR/manager/employee, перенос на следующий рабочий день и `carry_history`;
- пагинация и фильтры сотрудников;
- ограничения БД (уникальность, CHECK, пересечение отпусков).

## 9. Развёртывание

`docker-compose.yml`:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: hr
      POSTGRES_USER: hr
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U hr"]
      interval: 5s
      retries: 10

  backend:
    build: ./backend
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
    command: >
      sh -c "alembic upgrade head &&
             uvicorn app.main:app --host 0.0.0.0 --port 8000"

  frontend:
    build: ./frontend
    depends_on:
      - backend

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - frontend
      - backend

volumes:
  pgdata:
```

Почему так: один хост, три сервиса, одна команда запуска. Kubernetes и оркестрация
избыточны для диплома и отнимают время у функциональности и тестов.

Healthcheck: `GET /health` → `{ "status": "ok" }`. Логи — структурированные, с request id.

## 12. Definition of Done

Бэкенд считается готовым, когда:

- фронтенд работает без MSW (`VITE_USE_MOCKS=false`);
- все 4 роли проверены, чужие данные недоступны через прямые запросы;
- бизнес-правила нельзя обойти через клиент;
- `docker compose up` поднимает систему с нуля;
- миграции применяются на пустой БД;
- тесты проходят в CI;
- есть OpenAPI, ER-диаграмма, README и руководство пользователя;
- описаны допущения: отсутствие интеграции с 1С и бухгалтерией.

## 13. Почему не «модный» стек

| Соблазн | Почему не для диплома |
| --- | --- |
| Микросервисы | Один разработчик, один срок, одна БД. Комиссия спросит про отказоустойчивость и распределённые транзакции — придётся объяснять то, чего нет |
| MongoDB | Кадровый учёт — это связи и целостность. ER-модель и нормализация — ожидаемая часть ИСиТ |
| GraphQL | Фронтенду достаточно REST, а авторизация по полям и кэширование только усложнятся |
| Kafka/Celery/Redis | Нужны для тяжёлых фоновых задач. Для уведомлений хватит `BackgroundTasks`; иначе защита превратится в рассказ про инфраструктуру |
| Kubernetes | Избыточен. Docker Compose решает задачу демонстрации развёртывания |
| 1С:ЗУП | На вопрос «почему не 1С» ответ сильный: цель — **разработать** информационную систему, а не настроить готовый продукт; нужен кастомный веб-интерфейс и учёт проектной загрузки. Интеграцию с 1С можно указать в «развитии» |
| Low-code | Не демонстрирует проектирование БД, API и алгоритмов — а именно это оценивают |

## 14. Формулировка для защиты

> «Выбор обусловлен критериями: API-first SPA уже имеет REST-контракт; FastAPI даёт
> строгую валидацию и OpenAPI при минимальном boilerplate; PostgreSQL обеспечивает
> целостность и транзакционность для кадровых данных; модульный монолит выбран вместо
> микросервисов, потому что система разворачивается на одном узле, а сложность
> распределённой инфраструктуры не даёт функциональных преимуществ в рамках диплома.
> Все критичные правила — расчёт табеля, согласование отпусков, права доступа —
> реализованы на сервере, чтобы их нельзя было обойти через клиент».
