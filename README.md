# HR System — демо-система кадрового учёта

SPA на **React 19 + TypeScript + Vite 6** для кадрового учёта: сотрудники и справочники,
табель, отсутствия, кадровые события, загрузка и задачи по проектам,
оклады, отчёты и ролевая модель доступа.

Сейчас приложение работает на встроенном мок-бэкенде (**MSW v2**): реальные HTTP-запросы
к `/api/v1/...`, данные хранятся в `localStorage`. Код API-слоя готов к переключению на
**FastAPI** без изменения страниц и компонентов.

---

## Роли и доступ

| Раздел | admin | hr | manager | employee |
| --- | :---: | :---: | :---: | :---: |
| Дашборд | ✓ | ✓ | ✓ (своё подразделение) | — |
| Моя карточка `/me` | ✓ | ✓ | ✓ | ✓ |
| Сотрудники | ✓ | ✓ | ✓ (своё подразделение) | — |
| Орг-структура | ✓ | ✓ | ✓ (своя область) | — |
| Подразделения / должности | ✓ | ✓ | — | — |
| Проекты и назначения | ✓ | ✓ (создание и руководитель; команда — менеджер) | ✓ (создание; управление только своими, может передать проект) | — |
| Задачи по проектам | ✓ | ✓ (просмотр) | ✓ только по своим проектам | только свои, выполнить/перенести |
| Табель | ✓ | ✓ (правка + утверждение) | ✓ (просмотр и утверждение, своё подразделение) | только свой |
| Отсутствия | ✓ | ✓ (согласование) | ✓ (своё подразделение) | только свои |
| Загрузка | ✓ | ✓ | ✓ | только своя |
| Кадровые события | ✓ | ✓ (без увольнения) | ✓ (просмотр) | — |
| Оклад в карточке | ✓ | ✓ (чтение) | ✓ (только свой) | ✓ (свой) |
| Отчёты | ✓ | ✓ | ✓ | — |
| Пользователи | ✓ | — | — | — |
| Журнал действий | ✓ | — | — | — |

Роль `employee` не может открыть чужие данные через интерфейс: маршруты `/employees/:id`
редиректят на `/me`, а списки табеля, отсутствий и загрузки фильтруются на клиенте
по `employeeId`. Руководитель ограничивается своим подразделением при чтении, а проектами,
командой и задачами управляет только там, где назначен руководителем проекта.
Мок-бэкенд (MSW) проверяет сессию и роль на всех операциях чтения и записи по той же
матрице прав, что и клиент (`src/shared/lib/permissions.ts`): сотрудник видит только себя,
руководитель — подразделение с дочерними и команды своих проектов, HR — всех сотрудников.
Например, сотрудник не может прочитать чужую карточку, согласовать чужую заявку или
изменить табель через прямой вызов API.
При подключении FastAPI те же проверки нужно реализовать на сервере по матрице из
[`docs/API.md`](docs/API.md).

Подробная матрица и ограничения по ролям — в [`docs/ROLES.md`](docs/ROLES.md). HR не удаляет
сотрудников и не проводит увольнение, не создаёт заявки за сотрудников, но правит и
утверждает табель. Свою заявку на отсутствие HR оформляет
в «Моей карточке»; согласует её администратор. Оклад устанавливает только администратор;
HR видит оклады всех сотрудников, руководитель — только свой. Свой табель и свою заявку
может утвердить только admin; согласованные заявки не редактируются и не удаляются
напрямую — сначала возвращаются на согласование или отклоняются.

## Возможности

- **Аутентификация** — вход по email/паролю, хранение токена и пользователя в Zustand + `localStorage`,
  guard-компоненты `RequireAuth` / `RequireRole`, редирект на `/forbidden` и `/login`.
- **Учётные записи сотрудников** — при создании сотрудника можно поставить галочку
  «Создать учётную запись для входа». Без неё создаётся только кадровая карточка.
  С галочкой система генерирует временный пароль, показывает его один раз и требует
  сменить при первом входе (`/change-password`). Доступ можно создать позже из карточки
  сотрудника или раздела «Пользователи»; при увольнении учётная запись блокируется.
  Перед увольнением нужно переназначить активные задачи и выбрать новых руководителей
  проектов, иначе сохранение блокируется; подчинённые автоматически переходят
  к руководителю уровнем выше.
  HR может создавать только доступ с ролью «Сотрудник», остальные роли — прерогатива администратора.
- **Орг-структура** — дерево подразделений с руководителями и численностью, поиск по отделу,
  коду, руководителю или сотруднику, панель выбранного подразделения с составом и дочерними
  отделами. Admin/HR видят всё дерево, менеджер — свою область; сотруднику раздел недоступен.
- **Сотрудники** — плотная таблица с поиском, фильтрами по подразделению, должности, статусу и проекту,
  сортировкой, пагинацией, созданием/редактированием/удалением.
- **Карточка сотрудника** — табы: профиль, табель, отсутствия, проекты, задачи,
  история должностей и окладов; сводка задач в профиле; быстрые действия (заявка,
  событие, назначение, задача). История показывает график оклада и таблицу событий
  с подразделением, должностью, грейдом, окладом и автором.
- **Справочники** — подразделения (с иерархией и руководителями), должности
  (подразделение + профессиональная ветка + грейд + вилка оклада), проекты (статусы,
  менеджеры, участники). Повышение возможно только внутри подразделения и ветки,
  выше по грейду; смена подразделения — через перевод.
- **Табель** — сетка по дням месяца с кодами `Я`, `ОТ`, `Б`, `К`, `П`, `Н`, `В` и `—`
  (вне периода работы: до приёма или после увольнения);
  выходные и нерабочие праздничные дни 2026–2027 годов заполняются автоматически,
  для незнакомого года показывается предупреждение,
  отпуска/больничные/командировки подтягиваются из согласованных отсутствий,
  ручные правки хранятся как overrides; явки начисляются только с даты приёма сотрудника;
  правят отметки admin и HR (с записью в журнал); после утверждения табель заблокирован,
  но admin может внести аварийную правку — она помечается в журнале; статусы:
  черновик → на проверке → утверждён. Норма месяца считается по производственному
  календарю РФ: 2026 и 2027 годы — по 247 рабочих дней и 1972 часа при 40-часовой неделе;
  праздники отмечены красным, сокращённые дни — на час короче.
- **Отсутствия** — отпуск, больничный, командировка, неоплачиваемый отпуск, обучение;
  согласование/отклонение, расчёт рабочих дней, запрет пересекающихся заявок, влияние на статус
  сотрудника и табель. Согласованная заявка автоматически заполняет табель: отпуск и учёба — `ОТ`,
  больничный — `Б`, командировка — `К` (8 часов), неоплачиваемый — `Н`. Заявка «на согласовании»
  табель не меняет; согласованная заявка заменяет прежнюю ручную правку за эти дни.
  Больничный не согласуется, а **подтверждается** HR или администратором; руководитель
  не может подтвердить больничный, отклонить его тоже нельзя. В интерфейсе есть отдельная
  кнопка подтверждения и пометка «Подтверждён».
  При подтверждении больничного, согласовании командировки или отпуска активные задачи
  не блокируют заявку: по каждой задаче согласующий выбирает «оставить сотруднику»
  или «передать коллеге». Кандидаты — только участники проекта без согласованного
  отсутствия и с загрузкой меньше 100%.
- **Остатки отпусков** — 28 календарных дней по умолчанию, ручной перенос остатка,
  расчёт использованных и запланированных дней по заявкам; остаток виден в карточке
  сотрудника и проверяется при создании заявки.
- **Уведомления** — колокольчик в верхней панели: заявки на согласование, решения по
  заявкам, назначение и выполнение задач, передача проекта. На дашборде HR/admin есть
  блок «Требуют внимания». Каждое уведомление можно отметить прочитанным отдельно
  или прочитать все.
- **Кадровые события** — приём, перевод, повышение, увольнение, изменение оклада, отпуск;
  событие обновляет карточку сотрудника (подразделение, должность, оклад, статус).
  Повышение доступно из карточки сотрудника: выбирается новая должность, оклад по умолчанию
  равен нижней границе вилки; HR ставит минимум автоматически, admin может изменить оклад.
  Согласование заявки на отсутствие (отпуск, больничный, командировка, учебный отпуск,
  отпуск без сохранения) автоматически создаёт событие в ленте дашборда и в разделе
  «Кадровые события»; при изменении или удалении заявки событие обновляется/удаляется.
- **Проекты и команда** — admin и HR создают проекты и назначают руководителя;
  состав команды добавляет менеджер проекта, admin тоже может. HR видит команду,
  но не назначает участников. Manager создаёт проект с собой в роли руководителя. В списке проектов у manager есть
  переключатель «Мои проекты» / «Все проекты»: каталог доступен для просмотра, но
  команда, задачи и отчёт чужого проекта скрыты. Своими проектами manager управляет:
  добавляет/убирает участников и ставит задачи. Manager может передать свой проект
  другому сотруднику и после этого теряет к нему доступ. Удаление проекта — только admin/HR.
  При выборе участника видно текущее или ближайшее отсутствие с полным периодом
  (`Отпуск (сейчас): 16.11.2026 — 27.11.2026`, `Больничный (план): ...`); назначить
  сотрудника можно заранее.
- **Загрузка** — матрица «сотрудники × проекты» в процентах по **активным** назначениям
  (завершённые и будущие не учитываются), подсветка высокой загрузки и сотрудников без назначений.
  Итоговая загрузка по умолчанию не может превышать 100%; только администратор может
  разрешить перегруз до 150% с обязательной причиной.
- **Задачи по проектам** — менеджер (по своим проектам) или администратор ставит задачу
  участнику проекта с плановой датой и оценкой в часах. Сотрудник видит только свои задачи
  и может отметить их выполненными с комментарием результата (комментарий желателен,
  но не обязателен) или нажать «потребовалось больше времени» — задача перенесётся
  на следующий рабочий день с учётом праздников. В карточке задачи хранится количество,
  история переносов и история закрытия; результат видит руководитель. HR видит задачи
  в режиме просмотра.
- **Отчёты** — табель, загруженность проектов и команды (проекты, участники, роли,
  загрузка, отсутствия), остатки отпусков, загрузка, движение персонала, подразделения
  и должности; экспорт в Excel и печатная форма PDF через `window.print()`.
  Из карточки проекта можно открыть быстрый отчёт по этому проекту.
- **Дашборд** — численность, испытательный срок, активные проекты, средняя загрузка,
  отсутствующие сегодня, кликабельная ссылка на заявки на согласовании, ближайшие дни рождения
  (только admin/HR; менеджеру не показываются),
  динамика и распределение по подразделениям (Recharts). Лента событий показывает
  последние **созданные** изменения, а не события с самой поздней датой. Менеджер видит всё своё
  подразделение: своё, дочерние, подразделения где он руководитель, и команды своих
  проектов — те же люди, что и в списке сотрудников.
- **Администрирование** — создание учётных записей, управление ролями и блокировкой
  пользователей, статус «сменит пароль», журнал действий, сброс демо-данных к исходному набору.
- **UX** — светлая/тёмная тема, сворачиваемый sidebar, командная палитра (`Ctrl/Cmd + K`),
  RU-локаль, тосты, скелетоны, пустые и ошибочные состояния, адаптивность.

## Переменные окружения

Файл `.env.example`:

```env
VITE_API_URL=/api/v1
VITE_USE_MOCKS=true
```

- `VITE_USE_MOCKS=true` — включён MSW, данные в `localStorage` под ключом `hr-system-db-v1`.
- `VITE_USE_MOCKS=false` — MSW не запускается, axios отправляет запросы на `VITE_API_URL`.
- `VITE_API_URL` — базовый URL API. Для отдельного FastAPI-хоста можно указать
  `http://localhost:8000/api/v1` (не забудьте CORS на бэкенде).

### Подключение FastAPI

1. Создайте `.env.local` (или `.env.production`):

   ```env
   VITE_USE_MOCKS=false
   VITE_API_URL=http://localhost:8000/api/v1
   ```

2. Реализуйте эндпоинты по контракту [`docs/API.md`](docs/API.md) — фронтенд уже ожидает
   именно эти URL, тела запросов и формы ответов. План бэкенда, обоснование стека, схема БД
   и этапы реализации — в [`docs/BACKEND.md`](docs/BACKEND.md).
3. Перезапустите dev-сервер. Токен передаётся в заголовке `Authorization: Bearer <token>`,
   при `401` приложение разлогинивает пользователя.

Слой API находится в `src/shared/api/` (`client.ts` — axios и обработка ошибок, `index.ts` — методы),
а все типы контракта — в `src/shared/types.ts`.

## Тесты

```bash
npm test
```

Логика задач (`src/shared/lib/tasks.test.ts`) проверяет перенос через
выходные, отсчёт от сегодня для просроченных задач, определение «просрочено/на сегодня»
и сортировку. Тест табеля (`src/mocks/timesheet.test.ts`) проверяет, что явки не начисляются
до даты приёма и после даты увольнения, а ручные правки вне периода работы игнорируются.
Тест целостности демо-данных (`src/mocks/data.test.ts`) проверяет уникальность идентификаторов,
ссылки между сущностями и корректность диапазонов/дат. Правила повышения и перевода
(`src/mocks/domain/promotion.test.ts`) проверяются отдельно от HTTP и localStorage.
Миграция старого `localStorage` (`src/mocks/db.test.ts`), fallback-справочники
(`src/shared/lib/meta.test.ts`) и матрица прав (`src/shared/lib/permissions.test.ts`)
проверяются отдельными тестами, чтобы старые данные не роняли интерфейс.
Интеграционные тесты API (`src/mocks/handlers.test.ts`) прогоняют мок-бэкенд через MSW:
вход и пароли, сессионные и ролевые проверки, отсутствия (включая синхронизацию статуса
сотрудника и ленты событий), табель, задачи, пользователей, аудит и сброс данных.

Журнал последнего прохода по `ub-mode`: [`docs/UB-MODE-LOG.md`](docs/UB-MODE-LOG.md).

Браузерный smoke-набор лежит в `e2e/smoke.spec.ts` и запускается через Playwright.
Он проверяет вход и тёмную тему, роли, создание сотрудника, правку табеля,
согласование отсутствия, выгрузку Excel, focus trap и мобильную ширину.
Перед первым запуском нужен браузер: `npx playwright install chromium`.
CI выполняет `npm run test:e2e` отдельным job'ом.

## Демо-данные и сброс

- Мок-БД создаётся из `src/mocks/data.ts` при первом запросе и хранится в `localStorage`.
- Сбросить изменения: **Администрирование → Пользователи → «Сбросить демо-данные»**
  (доступно администратору), либо очистить ключ `hr-system-db-v1` в DevTools.
- Токен мока имеет вид `mock-<userId>` (например, `mock-u1`), поэтому после сброса БД
  может потребоваться повторный вход.

## Ограничения демо

- Нет реального бэкенда и серверной валидации — всё считается и хранится в браузере.
- Пароли в моке хешируются демонстрационным алгоритмом только ради того, чтобы не лежать
  в `localStorage` открытым текстом; для production нужен Argon2id/bcrypt на сервере.
- PDF — печатная форма браузера (стили `@media print`), а не серверная генерация.
- Журнал действий хранит последние 200 записей.
- Данные привязаны к браузеру/профилю; между устройствами не синхронизируются.

## Production-сборка

```bash
npm run build
npm run preview
```

Результат — `dist/`. Для SPA настройте fallback на `index.html` (history API).
Если планируете оставить моки в production-демо, файл `public/mockServiceWorker.js`
должен быть доступен по корню сайта; иначе соберите с `VITE_USE_MOCKS=false`.
